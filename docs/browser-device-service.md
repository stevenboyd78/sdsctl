# Experimental managed-browser service lifecycle

Status: **development candidate, isolated acceptance only**. This is not a
production installation or upgrade procedure. Use matching reviewed builds;
the published manual-login kiosk and remote TUI services remain unchanged.

This guide joins the existing setup steps and adds reviewable service files,
stopped-browser bundle updates and local unregistration. It does not install
Chromium, enable a service, replace a production display, save a password, or
change Home Assistant. Follow each step as the same non-root Linux display user.

## What belongs to one display?

Keep these paths separate, beneath an existing private directory owned by the
display account with mode `0700`. Do not put them in a personal browser profile.

| Item | Purpose | During a code-only update |
| --- | --- | --- |
| Installed Python environment | The reviewed application and its dependencies | Install the next build alongside it; retain the old one |
| Native profile | Device credential, CA certificates and recovery ledger | Keep the exact directory and contents |
| Public extension key | Stable extension identity; not a secret signing key | Keep the same reviewed key |
| Review bundle | Canonical extension code and runtime-pinned native helper | Stage a new directory; retain the old one |
| Dedicated Chromium directory | Browser-owned state and local native-host registration | Keep browser state; switch only the two registration files |
| Service review directory | Canonical launcher, settings and user unit | Prepare a new directory; retain the old one |

Never upgrade the old environment in place before maintenance. It is needed to
validate the existing bundle. A digest receipt or matching extension ID does not
authenticate an arbitrary publisher. Use a reviewed installed package and its
trusted interpreter; this candidate does not download, sign, publish or force
install extensions. It continues the dedicated-Chromium unpacked-bundle method
described in [managed startup](browser-device-startup.md). Google Chrome-branded
builds are not supported. Global browser policy and personal profiles are not
part of this workflow.

## 1. Complete first-time setup deliberately

For a new isolated display, follow these guides in order:

1. [Import its fresh private issuance](browser-device-profile.md).
2. [Prepare the canonical bundle](browser-device-bundle.md) with its reviewed public key.
3. [Register a new dedicated browser directory](browser-device-first-run.md).
4. [Open explicit setup, then test ordinary foreground startup](browser-device-startup.md).

Both native-helper TLS verification and browser trust must work for the exact
server origin. A certificate with the correct private IPv4 or IPv6 address is
supported; DNS names are optional. There is no requirement for a reverse proxy.
Do not add a TLS exception to complete acceptance.

Service preparation only proves offline file validity. It does not know whether
first-run confirmation was completed. Without that confirmation, the normal
startup page stays setup-required; the service never selects `--setup` for you.

## 2. Prepare and inspect service files

The examples use the fictional account `display` and an already installed,
reviewed environment at `/home/display/sdsctl-lab/runtime`. Substitute your exact
lab paths, not a production installation. The output directory must not exist.

```sh
/home/display/sdsctl-lab/runtime/bin/sdsctl browser-device-service --experimental create \
  --directory /home/display/sdsctl-lab/service-v1 \
  --browser-directory /home/display/sdsctl-lab/chromium-data \
  --bundle /home/display/sdsctl-lab/bundle-v1 \
  --profile /home/display/sdsctl-lab/native-profile \
  --public-key /home/display/sdsctl-lab/extension.pub.pem \
  --browser /usr/bin/chromium

/home/display/sdsctl-lab/runtime/bin/sdsctl browser-device-service --experimental check \
  --directory /home/display/sdsctl-lab/service-v1
```

The new mode-`0700` directory contains three mode-`0600` files:

- `service.json`: exact runtime and input paths, without credentials.
- `launch.py`: a fixed entry into the installed service checker and foreground launcher.
- `sdsctl-browser-device.service`: a graphical-session **user** unit, not a root service.

Review all three. The check compares generated bytes to this runtime's canonical
output and repeats the existing registration check. Changed files, extra files,
unsafe permissions, another runtime, or an interrupted/retired registration are
refused. A failed creation retains partial output and never retries over it.
Neither command loads scanner defaults, opens an application log file, launches
Chromium, contacts the server, or invokes `systemctl`.

The unit uses an absolute interpreter with Python isolated mode. Its command is
not interpreted by a shell, environment-variable substitution is disabled, and
systemd specifiers are escaped. Paths with spaces remain individual arguments.
Do not add dashboard passwords to the unit, its command line, or an environment
file. Same-account/root processes and the installed runtime remain trusted.

## 3. Review activation separately

Before installing the generated unit in an **isolated graphical session**, agree
which existing display service must be stopped and how it will be restored. Do
not run two display owners or reuse a production Chromium directory. Use the
desktop's existing graphical session; an SSH login or a lingering user manager
does not create one.

Validate the generated unit with the local systemd parser:

```sh
systemd-analyze --user verify /home/display/sdsctl-lab/service-v1/sdsctl-browser-device.service
```

A reviewed activation places that exact unit in the user's systemd unit directory,
reloads the user manager, then starts it. Before replacing an existing unit,
stop it, verify it is inactive with no remaining owned browser processes, compare
and retain its exact current contents, and review the replacement. Do not use a
blind overwrite or `enable --now` as an initial acceptance shortcut. Compare the
installed unit with the staged copy as well; the in-process checker cannot
protect a unit whose `ExecStart` was changed before it ran.

Only after session-start acceptance should the unit be enabled for the existing
`graphical-session.target`. Desktop-specific startup integration, autologin,
reboots and service takeover are separate acceptance steps, not actions performed
by this command. A desktop that does not manage this target requires its own
reviewed integration; do not start a fake target to bypass that requirement.

**The browser must finish closing before its display server stops.** The generated
user unit does not order a separate system service that owns the compositor (the
program drawing the graphical desktop). Review the
[browser-first session shutdown guide](browser-device-seat.md) before a session
stop/relaunch test. A desktop shutdown hook that merely starts cleanup in the
background is insufficient.

### Restart behavior

| Event | Behavior |
| --- | --- |
| Intentional browser close or normal service stop | Launcher returns `0`; no automatic restart |
| Browser crash | Launcher returns `75`; service may retry after 15 seconds |
| Unsafe configuration, unavailable graphical session or stale Chromium lock | Returns `78`; no automatic retry |
| CLI usage error | Returns `2`; no automatic retry |
| Repeated crashes | At most three starts within a 300-second window |
| Graphical session ends | Unit stops with that target; the desktop integration must wait for browser close before compositor teardown |
| Server is late or unavailable | Browser remains open; the existing bounded recovery logic handles it |
| Saved sign-out, rejected credential or TLS error | Existing pause/error stays intact; no automatic resume |

The policy uses systemd's [service restart controls](https://www.freedesktop.org/software/systemd/man/latest/systemd.service.html)
and [unit start limits](https://www.freedesktop.org/software/systemd/man/latest/systemd.unit.html).
On service stop, `KillMode=mixed` first signals the launcher. The launcher requests
Chromium's normal close with `SIGINT`, waits up to ten seconds, and kills its own
child only if that wait expires. Systemd still removes remaining service processes;
the unit's stop timeout is twenty seconds. This avoids sending `SIGTERM` directly
to all Chromium processes: Linux Chromium treats that signal as fast session
ending, which can leave profile locks behind even when it exits with status zero.
Neither path deletes or bypasses a Chromium lock. A forced shutdown can still
leave markers requiring review before the next launch.
See Chromium's [Linux signal handling](https://github.com/chromium/chromium/blob/152.0.7977.75/chrome/browser/chrome_browser_main_posix.cc)
and systemd's [mixed shutdown policy](https://www.freedesktop.org/software/systemd/man/latest/systemd.kill.html).

Starting a service is not proof that a display has a verified session or live
scanner data. A new graphical session may start an enabled unit again; that does
not clear a persisted device sign-out.

An asynchronous compositor shutdown can still leave Chromium markers even when
the browser service reports exit status zero. Check completion, owned processes
and all three markers; a successful `systemctl stop` alone is not acceptance.

**Abrupt power-loss recovery is still a gate.** Chromium singleton markers,
including stale markers, are deliberately not removed. A physical cold-start
test must not declare success by deleting them or resetting browser storage.

## 4. Update code without replacing the display identity

This candidate supports a same-identity registration switch, **not** a credential,
CA, origin, device-ID, extension-key or recovery-schema migration. Those require
separate reviewed procedures. No extension distribution/update acceptance is
claimed solely from an offline command passing.

1. Install the reviewed next build in a separate Python environment. Retain the
   old environment unchanged. Review package provenance and compatibility first.
2. Stop the display service and foreground launcher. Verify that Chromium closed
   normally. The maintenance tool refuses a held launcher lock or any Chromium
   singleton marker; it never stops/kills a browser or removes those markers.
3. Use the **new** environment's `browser-device-bundle --experimental create` to
   prepare a new bundle using the **existing** native profile and public key.
4. Review the new bundle, then run the following with your exact paths:

```sh
/home/display/sdsctl-lab/runtime-next/bin/sdsctl browser-device-maintenance --experimental update \
  --directory /home/display/sdsctl-lab/chromium-data \
  --bundle /home/display/sdsctl-lab/bundle-v1 \
  --replacement-bundle /home/display/sdsctl-lab/bundle-v2 \
  --profile /home/display/sdsctl-lab/native-profile \
  --public-key /home/display/sdsctl-lab/extension.pub.pem \
  --previous-python /home/display/sdsctl-lab/runtime/bin/python \
  --backup /home/display/sdsctl-lab/update-v1-to-v2-review \
  --confirm-stopped-maintenance
```

The old interpreter performs a bounded, isolated offline check of the old
registration. It is selected explicitly, never read from a receipt. The new
runtime independently validates the new bundle against its own packaged code.
The identity must match. The tool preserves the original two registration files
in a new private backup before removing the old completion receipt and changing
the native-host manifest. The new receipt is published only after the new
manifest is durable. Browser storage, alarms, cookies, native recovery state,
credentials and trust are not copied, edited or reinitialized.

5. Prepare a **new** service review directory using the new environment and
   bundle. Check it offline. The old service now fails its registration check;
   do not edit its settings to bypass canonical verification.
6. Review and replace the stopped service unit, reload the user manager, and
   perform controlled startup acceptance. Confirm that the same extension ID
   retains its browser state when Chromium loads the new unpacked path. Test a
   paused/rejected device as well as a healthy one before calling updates accepted.

On any maintenance error, stop and retain the backup and all original files.
An interrupted switch can leave a missing receipt or maintenance guard; both
block ordinary startup. `completed.json` records durable preparation of the
result, but an error near the final guard removal can still mean the outcome is
unconfirmed. Inspect it offline; do not repeat over the backup, copy old receipts
back, erase a guard, or reset a ledger. There is deliberately no automatic rollback
or generic state-migration shortcut.

## 5. Remove this local registration safely

First revoke the **exact device** at its server authority and confirm the outcome,
including session denial. Stop/disable its exact user service and confirm the
owned browser is gone. Local file removal alone is not credential invalidation.

Run `browser-device-maintenance --experimental retire` with the same
`--directory`, `--bundle`, `--profile`, `--public-key`, `--previous-python`,
`--backup`, and `--confirm-stopped-maintenance` options as above, but **without**
`--replacement-bundle`. Select the currently registered bundle/runtime and a new
backup directory.

Retirement retains the original receipt and native-host manifest in that backup,
removes exactly those two active registration files, and leaves a permanent
retirement guard. It does not recursively delete a directory, remove the
credential, clear browser state, revoke at the server, touch a trust store, or
remove/disable a systemd unit. Old and new launchers cannot use a retired
registration. Re-running retirement fails instead of silently restoring it.

After confirmed revocation and local retirement, inventory the exact installed
unit, staged service directories, bundles, native profile, Chromium directory and
extra downloaded credentials. Review permanent deletion separately. Retain only
the evidence/backups explicitly required; they are private and may contain
identifying paths. Do not delete a shared environment or public key used by
another display. No broad home-directory, wildcard or recursive cleanup command
is provided here.

## Acceptance still required

Deterministic file/CLI tests and systemd syntax verification are not physical or
production acceptance. Isolated installed old/new-runtime and real-Chromium tests
passed state retention across bundle-path updates, close/crash policy, terminal
failures and local retirement. A separate
[HDMI normal-session test](browser-device-seat.md#what-the-physical-test-established)
passed with the stated compositor-ordering and keyring limitations. These do not
qualify arbitrary desktop wiring or unattended production startup. Before release,
complete the remaining physical/production checks, including both Pi geometries,
secure keyring handling and combined display/server outage recovery. Explicit device
replacement/resume, trusted production extension distribution and abrupt-crash
profile ownership remain separate security gates. Keep both production TUIs
unchanged until a separately approved deployment and restoration plan exists.
