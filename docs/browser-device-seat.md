# Experimental browser-first graphical-session shutdown

Status: **development guidance for an isolated test, not a production installer**.
Start with the [managed-browser service guide](browser-device-service.md). This
page does not create a desktop account, install a compositor, enable startup,
replace a TUI, or change the released manual-login kiosk service.

## Why the browser has to close first

The **compositor** is the program that provides the graphical display; labwc is
one example. Chromium needs that display to remain available while it closes.
The browser service and a separate system service running the compositor belong
to different service managers. The browser unit's `PartOf=graphical-session.target`
alone does not order shutdown of that system service.

The required normal-stop sequence is:

1. Request the dedicated user session and its browser services to stop.
2. Wait for the stop operation to finish while the compositor is still running.
3. Check the service results, owned processes and Chromium's remaining markers.
4. Let the compositor stop. Relaunch only after all checks pass.

In labwc 0.9.8, the shutdown script is launched asynchronously. Waiting inside
that script does not make labwc wait for it. See labwc's
[session hooks](https://github.com/labwc/labwc/blob/0.9.8/src/config/session.c)
and [asynchronous child launcher](https://github.com/labwc/labwc/blob/0.9.8/src/common/spawn.c).
Do not assume another compositor or version has the same behavior; qualify the
actual installation. A sleep or a background `systemctl --no-block stop` is not a
completion check.

## Review the dedicated seat before changing it

Here, **seat service** means the existing, separately reviewed system service
that owns this one test compositor. It is not the generated browser user unit.
The example assumes all of the following:

- An isolated non-root account named `display`, used for no personal desktop work.
- A reviewed compositor service with `User=display`, its own console and working
  PAM/logind session. Its user bus stays available throughout normal seat stop.
- The actual compositor startup activates the dedicated
  `sdsctl-browser-seat-session.target`, tied to the real `graphical-session.target`.
  Neither target is started artificially from SSH to bypass session checks.
- The generated `sdsctl-browser-device.service` and a separately reviewed,
  mutually exclusive `sdsctl-browser-setup.service` both stop with that session.
  The setup service and dedicated session target are **example integration names**,
  not files generated by `browser-device-service create`.
- The existing, canonical browser directory is
  `/home/display/sdsctl-lab/chromium-data`, not a symlink or personal profile.
- An exact takeover/restoration plan preserves the production TUI, its font,
  credentials, installed runtime and boot enablement.

If the actual integration differs, review the exact account, paths, units and
dependencies first. In particular, stopping a shared graphical target would stop
other desktop applications. Do not apply this example to a shared user session.

## Synchronous stop helper example

Review this as `/usr/local/libexec/sdsctl-browser-seat-stop`. Installation must
be a separate approved action: the helper and its parent directories should be
root-owned and not writable by the display account. It **runs as `display`**, not
root. Its environment must resolve trusted system `id` and `systemctl` commands.
Use your reviewed exact browser path and service names; a missing path, bus or
service is a failure to inspect, not a reason to skip a check.

```sh
#!/bin/sh
set -eu
test "$(id -un)" = display
export XDG_RUNTIME_DIR="/run/user/$(id -u)"
export DBUS_SESSION_BUS_ADDRESS="unix:path=$XDG_RUNTIME_DIR/bus"
test -S "$XDG_RUNTIME_DIR/bus"
browser_directory=/home/display/sdsctl-lab/chromium-data
test -d "$browser_directory"
test ! -L "$browser_directory"

systemctl --user stop sdsctl-browser-seat-session.target graphical-session.target
test "$(systemctl --user show sdsctl-browser-seat-session.target -p ActiveState --value)" = inactive
test "$(systemctl --user show graphical-session.target -p ActiveState --value)" = inactive
for unit in sdsctl-browser-device.service sdsctl-browser-setup.service; do
    test "$(systemctl --user show "$unit" -p LoadState --value)" = loaded
    test "$(systemctl --user show "$unit" -p ActiveState --value)" = inactive
    test "$(systemctl --user show "$unit" -p MainPID --value)" = 0
    test "$(systemctl --user show "$unit" -p Result --value)" = success
    test "$(systemctl --user show "$unit" -p ExecMainStatus --value)" = 0
done
for item in SingletonLock SingletonSocket SingletonCookie; do
    test ! -e "$browser_directory/$item"
    test ! -L "$browser_directory/$item"
done
printf '%s\n' 'Browser stop checks passed; compositor may now terminate.'
```

Both `-e` and `-L` matter: a dangling symlink is still a Chromium marker. This
helper never deletes markers or repairs state. The additional directory, unit-load
and dedicated-target checks make the reusable example reject more configuration
mistakes than the original physical-test helper; this generalized example is
shell-tested separately, not claimed to have been installed on the Pi.

For a seat with **no existing `ExecStop`**, the reviewed drop-in would contain:

```ini
[Service]
ExecStop=/usr/local/libexec/sdsctl-browser-seat-stop
TimeoutStopSec=45s
```

This belongs to the **compositor's system service**, not
`sdsctl-browser-device.service`. Preserve its `User=display` and existing session
configuration. Do not add a `+` privilege prefix or `-` failure-ignore prefix.
If the seat already has stop commands, review their ordering and purpose; do not
blindly append this after a command that terminates the compositor or reset the
existing list. Keep the generated browser user unit unchanged.

Systemd runs a synchronous `ExecStop` before its normal process termination.
The example allows 45 seconds for the helper, versus the browser unit's 20-second
stop timeout; review the total budget of any other session services too. A failing
or timed-out helper reports failure but **does not veto compositor termination**.
An unexpected compositor exit may also make orderly browser close impossible;
startup failures can skip `ExecStop` entirely. Do not treat `ExecStopPost` as an
equivalent before-close hook. See the
[systemd service reference](https://www.freedesktop.org/software/systemd/man/latest/systemd.service.html#ExecStop=).

## Check results before any relaunch

Use separate stop, inspect and start steps during acceptance, not a combined
restart that can launch again before an operator reviews a failure. Record the
old seat/browser PIDs and inspect their exact service groups after stop. MainPID
zero alone does not prove there are no descendants; check the owned Chromium,
crash-reporting and compositor processes as well as the unit result and all three
Singleton markers. Never use a blanket kill command against other browsers.

If the stop fails, the bus disappears early, a process remains, or a marker is
present, preserve the profile and logs and stop the test. Do not clear a lock,
reset a service failure, copy a completion receipt, reinitialize setup, or weaken
TLS/sandbox settings to obtain a passing restart. Restore the approved production
display only after the test's owned display processes are gone. Changing the
normal-stop ordering does not recover a previously abandoned Chromium profile.

## What the physical test established

An isolated HDMI test used Debian 13/aarch64, Chromium 152.0.7977.75, labwc 0.9.8
and systemd 257.13, with a fictional loopback HTTPS authority and no scanner daemon.
The original asynchronous-hook case left all three markers despite browser-service
exit status zero; it was preserved unchanged and the production TUI restored.

A separately approved fresh profile with a synchronous non-root seat `ExecStop`
passed browser-first close and actual graphical-session relaunch. Ordinary
authentication returned on the saved renewal schedule without repeated setup.
Real page sign-out remained paused after another session relaunch, with no new
authentication exchanges. The operator confirmed healthy restart and the final
restored production TUI updating. No locks or browser state were reset.

These results are limited to **normal session stop/relaunch**. The ordinary user
unit was manually started after the real graphical target returned; enablement,
full user-manager restart, host reboot and power cuts were not tested. The test
account reused an operator-created blank-password keyring; secure unattended
keyring handling is not qualified or recommended by this example. Live scanner
data, the small Pi, combined server/display outage, trusted production extension
distribution and abrupt-power-loss profile ownership remain separate checks.
